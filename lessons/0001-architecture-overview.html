Lesson 1

The Big Picture

How the pieces fit together — and why they're split this way.

The One-Line Summary

This is a 2D animated slideshow editor where the frontend owns all the intelligence (scene graph, animation, rendering) and the backend is a thin persistence layer.

Key insight: The engine is a pure TypeScript class library with zero React or DOM dependencies. It could run in a Web Worker or Node.js. This is the single most important architectural decision in the codebase.

Four Layers

The frontend has four distinct layers, each depending only on the one below:

Layer 4 — UI React Components Zustand Stores │ Layer 3 — Glue App Layer (EngineProvider, Persistence, LibrarySync) │ Layer 2 — Mutation Command System (89 command types, undo/redo) │ Layer 1 — Domain Engine (Scene Graph, Animation, Evaluation) │ Backend FastAPI + SQLite (stores JSON blobs, serves assets)

Layer 1: Engine frontend/src/engine/

The pure domain model. 76 files. Contains the scene graph, animation evaluator, keyframe interpolation, IK solver, constraint system, mesh deformation, and serialization. No React. No DOM. No HTTP.

Key files:

  • engine.ts — the root class, owns all managers
  • sceneNode.ts — a node in the scene tree (transform, components, children)
  • animationEvaluator.ts — evaluates keyframes at a given time
  • commands/ — 89 command files, one per mutation type
  • lessonSerializer.ts — JSON serialization/deserialization (704 lines)

Layer 2: Command System frontend/src/engine/commands/

Every mutation goes through a Command object with validate() + execute() that returns an Inverse payload. This enables undo/redo and transaction batching.

UI Action → dispatch(command) → command.validate(engine) // throws on invalid → command.execute(engine) // mutates state, returns inverse → undoStack.record(inverse) // enables undo

See Refactoring.Guru — Command Pattern for the canonical pattern reference.

Layer 3: App Layer frontend/src/app/

The glue between React and the engine. Handles:

  • EngineProvider.tsx — React context providing the engine to the component tree
  • persistence.ts — autosave, dirty tracking, recovery shadows
  • librarySync.ts — bridges Zustand stores to engine definitions
  • lessonTransfer.ts — import/export of .lesson files

Layer 4: Stores + UI frontend/src/stores/ + frontend/src/components/

26 Zustand stores for transient UI state (selection, playback, panels, etc.). React components read from stores and dispatch commands.

The Backend backend/

Intentionally thin. FastAPI + SQLAlchemy + SQLite. Serves five resource types:

ResourceEndpointStores
Projects/api/projectsJSON blobs (opaque)
Assets/api/assetsImage files + metadata
Materials/api/materialsParameter definitions
Shaders/api/shadersGLSL source + uniforms
Clips/api/clips/libraryReusable animation presets
Why opaque blobs? The backend stores projects as raw JSON strings, not normalized relational data. This means the backend cannot query project internals — it's a file server with extra steps. This is a deliberate trade-off: simplicity over queryability.

Data Flow

┌─────────────────────────────────────────────────┐ │ User clicks "Add Keyframe" │ │ │ │ React UI │ │ → dispatch(AddKeyframeCommand) │ │ → command.validate(engine) │ │ → command.execute(engine) │ │ → engine mutates NodeAnimation │ │ → engine fires EventBus event │ │ → Renderer re-evaluates affected node │ │ → Zustand store updates selection │ │ → PersistenceService marks dirty │ │ → undoStack records inverse │ │ │ │ Autosave (debounced) │ │ → engine.toJSON() │ │ → POST /api/projects (JSON blob) │ └─────────────────────────────────────────────────┘

Key Architectural Decisions

  1. Engine is framework-agnostic. No React, no DOM, no HTTP. Could run in a Web Worker.
  2. Backend is a dumb store. All business logic lives in the frontend.
  3. Scene-per-slide. Each slide has its own Scene with its own root node tree and camera. Slides are independent.
  4. Command pattern with inverse. Every mutation is reversible. Transactions group commands for atomic undo.
  5. Immutable components. NodeComponents are Object.freeze()'d. Change requires replacing the whole object.
  6. Event bus for reactivity. The engine fires ~50 event types. The renderer subscribes and selectively updates.
