Lesson 3

The Command System

How every mutation flows through validate → execute → record, and how undo works.

The Core Idea

Every mutation in the editor — creating a node, moving a keyframe, renaming a slide — goes through the same pipeline. No exceptions. This gives you undo/redo, transaction batching, validation, logging, and AI proposal execution for free.

Dispatch Flow UI Action → dispatch(command) → command.validate(engine) // throws on invalid → command.execute(engine) // mutates state, returns inverse → undoStack.record(inverse) // enables undo → onCommandSucceeded() // triggers autosave

The Command Interface commands/command.ts

12 lines. This is the contract every command implements:

interface Command<Inverse> {
  readonly type: string
  readonly parameters: Readonly<Record<string, unknown>>
  validate(engine: Engine): void       // throw to reject
  execute(engine: Engine): Inverse     // mutate + return undo data
  toJSON(): Record<string, unknown>    // for serialization
}
The inverse pattern: execute() returns an Inverse — a payload containing exactly the information needed to undo the command. The dispatcher stores this on the undo stack. To undo, you dispatch a new command that applies the inverse.

The Dispatcher commands/dispatcher.ts

Wires everything together. 85 lines total:

dispatch<Inverse>(command: Command<Inverse>): CommandResult<Inverse> {
  try {
    command.validate(this.#engine)       // 1. validate
    const inverse = command.execute(this.#engine)  // 2. execute
    this.#undoStack.record({             // 3. record
      id: newId('command'),
      type: command.type,
      parameters: command.parameters,
      inverse,
    })
    this.#onCommandSucceeded?.()         // 4. trigger autosave
    return { ok: true, inverse }
  } catch (error) {
    return { ok: false, error }          // validation failed
  }
}

If validate() throws, the command is rejected — no state change, no undo entry. If execute() throws (shouldn't happen after validation), same result.

The Undo Stack commands/undoStack.ts

A simple list of entries, newest first:

interface UndoStackEntry<Inverse> {
  id: string
  type: string           // e.g. 'MoveNode', 'CreateNode'
  parameters: Record     // what the command did
  inverse: Inverse       // how to undo it
}

The stack is in-memory and session-scoped. It clears on project load and is never serialized into the .lesson file.

How Undo Actually Works

There is no undo() method. Undo is performed by dispatching a new command that applies the inverse. For example, to undo a MoveNode:

// MoveNode was: { nodeId: 'abc', x: 100, y: 200 }
// Inverse was:  { nodeId: 'abc', oldX: 50, oldY: 75 }

// Undo = dispatch a new MoveNode to the old position
dispatcher.dispatch(new MoveNodeCommand({
  nodeId: 'abc',
  x: inverse.oldX,    // 50
  y: inverse.oldY,    // 75
}))

This means every undo is itself a forward command that pushes a new entry onto the stack. The history grows in both directions.

Example Commands

Simple: MoveNode commands/moveNodeCommand.ts

class MoveNodeCommand implements Command<MoveNodeInverse> {
  type = 'MoveNode'

  validate(engine) {
    engine.getNode(this.#nodeId)  // throws if not found
    requireFiniteNumber(this.#x, 'X')
    requireFiniteNumber(this.#y, 'Y')
  }

  execute(engine) {
    const { transform } = engine.getNode(this.#nodeId)
    engine.setTransform(this.#nodeId, { ...transform, x: this.#x, y: this.#y })
    return { nodeId: this.#nodeId, oldX: transform.x, oldY: transform.y }
  }
}

The inverse captures the previous state (oldX, oldY), not the delta. This is simpler and more reliable.

Medium: CreateNode commands/createNodeCommand.ts

class CreateNodeCommand implements Command<CreateNodeInverse> {
  type = 'CreateNode'

  validate(engine) {
    if (this.#name.trim() === '') throw new Error('Name must not be empty')
    if (this.#id && nodeExists(engine, this.#id)) throw new Error('ID already exists')
    const scene = engine.getScene(this.#sceneId)
    if (!scene.getNode(this.#parentId)) throw new Error('Parent not found')
    if (this.#components?.camera && scene.camera) throw new Error('Camera already exists')
  }

  execute(engine) {
    const node = engine.createNode(this.#sceneId, this.#parentId, this.#name, { ... })
    return { nodeId: node.id }  // inverse: just the ID (for delete-on-undo)
  }
}

The inverse is minimal — just the node ID. To undo, you'd dispatch a DeleteNodeCommand with that ID.

Composition: TransactionCommand commands/transactionCommand.ts

Batches multiple commands as one undo entry:

class TransactionCommand implements Command<TransactionInverse> {
  type = 'Transaction'
  #children: Command[]

  validate(engine) {
    for (const cmd of this.#children) cmd.validate(engine)  // all must be valid
  }

  execute(engine) {
    const children = []
    try {
      for (const cmd of this.#children) {
        children.push({ type: cmd.type, inverse: cmd.execute(engine) })
      }
    } catch (error) {
      // rollback: undo everything that succeeded
      for (const child of children) restoreMove(engine, child.inverse)
      throw error
    }
    return { children }
  }
}
Atomic rollback: If any child command fails during execution, the transaction rolls back all completed children. The undo stack never gets a partial entry. This is critical for multi-command gestures like numeric drags in the Inspector.

Engine vs EnginePublic engine/internal.ts

The engine has a dual-face design:

InterfaceAudienceHas mutation methods?
EngineCommands onlyYes (createNode, setTransform, etc.)
EnginePublicUI, Renderer, StoresNo. Read-only queries + evaluateNode

toReadOnly(engine) wraps the internal engine in a read-only proxy. The UI never calls mutation methods directly — it always goes through dispatcher.dispatch(command).

// UI code — cannot mutate directly
const { engine, dispatch } = useEngine()
const node = engine.getNode('abc')           // ✓ read
dispatch(new MoveNodeCommand({ ... }))        // ✓ mutate via command

engine.setTransform('abc', { ... })           // ✗ doesn't exist on EnginePublic
Why? This enforces a single mutation path. Every change flows through the dispatcher, which validates, executes, records the inverse, and triggers autosave. No way to accidentally bypass the system.

The Command System's Role in AI

AI proposals are just batches of commands. The AI generates an AIEditProposal containing command objects. The user approves → the commands execute as a transaction. The same validate → execute → record pipeline runs.

This is why the command system exists: it makes every mutation (human or AI) reversible, testable, and observable.

Complete Data Flow

┌─────────────────────────────────────────────────┐ │ User drags a node on the canvas │ │ │ │ Canvas mouseup │ │ → inspectorActions.moveNode(nodeId, x, y) │ │ → dispatch(MoveNodeCommand) │ │ → validate: node exists, x/y finite │ │ → execute: engine.setTransform(...) │ │ → node.markDirty() cascades │ │ → EventBus fires TransformChanged │ │ → Renderer re-evaluates node │ │ → undoStack.record({ oldX, oldY }) │ │ → onCommandSucceeded() │ │ → persistenceService marks dirty │ │ → autosave debounce starts │ └─────────────────────────────────────────────────┘

Key Design Decisions

  1. Single mutation path. No way to bypass validation. No accidental state changes.
  2. Inverse, not delta. Store the previous state, not the change. Simpler, more reliable undo.
  3. Undo = forward command. Undo dispatches a new command. History grows linearly.
  4. Transactions are atomic. Partial failure → full rollback. No partial undo entries.
  5. 89 commands, not 89 methods. Each mutation is a separate class. Testable in isolation.
  6. AI uses the same path. AI proposals are command batches. No special case.
