Lesson 5

Persistence & Autosave

How your work survives crashes, tab closes, and network failures.

Three Layers of Protection

The persistence system has three independent safety nets:

Layer 3 — Backend Save POST /api/projects (debounced, retried on failure) ↑ Layer 2 — Recovery Shadow IndexedDB (written on every command + every 30s) ↑ Layer 1 — Dirty Flag Zustand Store (marks work as needing save)

The Dirty Flag stores/persistenceStore.ts

The simplest piece — 13 lines total:

const usePersistenceStore = create()((set) => ({
  dirty: false,
  markDirty: () => set({ dirty: true }),
  markSaved: () => set({ dirty: false }),
}))

Every successful command marks dirty. A successful save marks saved. The autosave loop checks dirty before saving — no dirty flag, no save.

The PersistenceService app/persistence.ts

The orchestrator. 156 lines that wire commands to saves:

On Every Successful Command

onCommandSucceeded: () => {
  ensureTimer()              // start 30s periodic timer if not running
  markDirty()                // flag for autosave
  writeRecoveryShadow()      // crash protection (Layer 2)
  requestAutosave()          // schedule debounced save (Layer 3)
}

Debounced Save

requestAutosave() uses setTimeout(0) — it coalesces rapid command sequences into one save. If you move a node 10 times in 100ms, only one save fires after the last move.

requestAutosave() {
  if (scheduledId !== null) return  // already scheduled
  scheduledId = setTimeout(() => {
    scheduledId = null
    autosave()
  }, 0)
}

Periodic Save

A 30-second interval (AUTOSAVE_INTERVAL_MS) catches any commands that slipped through the debounce:

setInterval(() => {
  writeRecoveryShadow()
  autosave()
}, 30000)

In-Flight Protection

If a save is already in progress (saveInFlight), new saves are queued (saveAgain = true). When the in-flight save completes, it checks the flag and saves again if needed. This prevents overlapping network requests.

Command fires → markDirty + writeShadow + requestAutosave → setTimeout(0) coalesces → performSave() → if saveInFlight: set saveAgain, return → else: upsert to backend → on success: markSaved → on failure: notify + markUnavailable → finally: if saveAgain: performSave()

Project Generation

When a new project loads, projectGeneration increments. This prevents stale saves from marking a fresh project as saved. If the generation changed during an in-flight save, the save result is discarded.

Recovery Shadow app/recoveryShadow.ts

Crash protection via IndexedDB. Two keys:

KeyPurpose
recoveryShadowLatest project JSON (written on every command + 30s timer + beforeunload)
recoveryLastSavedLast successfully saved JSON (written after backend upsert)

How Recovery Works

hasRecoverableShadow(): Promise<boolean> {
  shadow = await readShadow()
  lastSaved = await readLastSaved()
  return shadow !== null && shadow !== lastSaved
}

If the shadow differs from the last save, there's unrecoverable work. On next load, the app offers to restore from the shadow.

Why IndexedDB, not localStorage? The project JSON can be large (embedded assets are base64). IndexedDB has no 5MB limit, supports async writes, and doesn't block the main thread.

Beforeunload Handler

window.addEventListener('beforeunload', () => {
  writeRecoveryShadow()
})

When the user closes the tab, the shadow is written synchronously (IndexedDB's put() is fast enough). This catches the "close before autosave fires" scenario.

The .lesson File Format

A single JSON file with versioned structure:

{
  "version": 1,
  "project": {
    "id": "...",
    "name": "...",
    "slides": [...]
  },
  "clips": [...],           // reusable animation presets
  "ikChains": {...},        // IK chain data
  "constraints": {...},     // node constraints
  "library": {              // optional: embedded definitions
    "assets": [...],        //   asset definitions with base64 image data
    "materials": [...],     //   material definitions
    "shaders": [...]        //   shader definitions with GLSL source
  }
}

Self-Contained by Default

The library section carries snapshots of every definition the project references. This means a .lesson file restores fully on another machine — even if the original assets were deleted from the library.

Slim (Reference-Only) Files

Older v1 files may reference definitions without embedding them. These are "slim" — they work only if the definitions exist in the backend library. The editor handles both formats.

Validation Pipeline

validate(json) → string[]    // returns error messages
// then: buildProjectFromJSON(json) → Project
// then: parseClipsFromLessonJSON(json) → ClipDefinition[]
// then: restore IK + constraints from JSON

Asset Embedding app/assetSnapshot.ts

Before saving, referenced assets are fetched and embedded as base64:

ensureReferencedEmbedded(engine) {
  referenced = collectReferencedDefinitionIds(project)
  await Promise.all(referenced.map(id => captureAssetSnapshot(engine, id)))
}

captureAssetSnapshot(engine, definitionId) {
  if (engine.getEmbeddedAsset(definitionId)) return true  // already embedded
  definition = libraryDefinition(definitionId)
  bytes = await fetchImageBytes(definition.original_url)   // fetch + base64
  engine.embedAsset({ id, name, data: bytes.data, mimeType, metadata })
}

Material and shader definitions are embedded synchronously (definitionSnapshot.ts) — no image data to fetch.

Import / Export app/lessonTransfer.ts

Import

importLessonFile(engine, file) {
  text = await file.text()
  json = JSON.parse(text)
  errors = validate(json)           // schema validation
  freshJson = withFreshProjectId(json)  // new ID to avoid collisions
  engine.restoreFromJSON(freshJson)
  restoreProjectInEditor(engine)
}

Download

downloadLessonCopy(engine) {
  await ensureReferencedEmbedded(engine)      // embed assets
  ensureReferencedMaterialAndShaderSnapshots(engine)  // embed defs
  blob = new Blob([JSON.stringify(engine.toJSON())])
  // trigger browser download as {name}.lesson
}

Backend Communication

The backend stores projects as opaque JSON blobs:

ProjectsApi.upsert(blob: string) → POST /api/projects
ProjectsApi.get(id) → GET /api/projects/{id} → string (JSON)
ProjectsApi.list() → GET /api/projects → ProjectSummary[]

The backend cannot query project internals — it's a file server with extra steps. This is a deliberate trade-off: simplicity over queryability.

Offline support: When the backend is unavailable, the editor keeps working. The status bar shows "Backend unavailable" and saves are skipped. The recovery shadow still protects against crashes. When the backend returns, the next autosave succeeds.

Complete Save Flow

User moves a node → dispatch(MoveNodeCommand) → validate → execute → undoStack.record → onCommandSucceeded() → markDirty() → writeRecoveryShadow() ← IndexedDB (crash protection) → requestAutosave() → setTimeout(0) ← debounce → performSave() → ensureEmbedded() ← fetch + base64 assets if needed → engine.toJSON() ← serialize to LessonJSON → JSON.stringify() ← to blob string → POST /api/projects ← backend save → recordLastSaved() ← IndexedDB (for recovery comparison) → markSaved() ← clear dirty flag

Key Design Decisions

  1. Three independent safety nets. Dirty flag, recovery shadow, backend save. Each catches different failure modes.
  2. Debounce + periodic. Coalesces rapid commands; periodic timer catches stragglers.
  3. IndexedDB for shadows. No size limit, async, non-blocking. localStorage is too small for embedded assets.
  4. Self-contained .lesson files. Embedded definitions restore on any machine. No dependency on the backend library.
  5. Opaque backend blobs. The backend doesn't parse project JSON. Simpler backend, dumber persistence.
  6. Offline-first. The editor works without the backend. Saves queue until connectivity returns.
