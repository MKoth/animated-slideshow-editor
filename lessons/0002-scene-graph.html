Lesson 2

The Scene Graph

How nodes, transforms, and components compose into a scene.

What Is a Scene Graph?

A scene graph is a tree of nodes. Each node has a position in space (transform) and an identity (components). Parenting composes transforms: a child's position is relative to its parent.

In this project, every slide has exactly one scene, and every scene has exactly one root node and one camera node.

Scene ├── root (SceneNode) │ ├── Character (assetInstance component) │ │ ├── Head (assetInstance component) │ │ └── Left Arm (bone component) │ ├── Speech (text component) │ └── Table (table component) └── camera (SceneNode, camera component) └── drives the viewport (pan = position, zoom = scale)

SceneNode engine/sceneNode.ts

The fundamental unit. Every visible (and invisible) thing in a slide is a SceneNode.

class SceneNode {
  id: string                        // unique within the project
  name: string                      // human-readable label
  parent: SceneNode | null          // null for root
  children: SceneNode[]             // ordered (z-order = index)
  transform: Transform              // local-space placement
  visible: boolean                  // render toggle
  opacity: number                   // 0..1
  material: MaterialInstance        // tint, opacity, uniforms
  components: NodeComponents        // identity (frozen)
  clipInstances: ClipInstance[]     // assigned animation clips
}

The Key Insight: Identity Is Components, Not Type

A node is not "a text node" or "an asset node." A node is a SceneNode whose components define what it is. The same node could theoretically carry different components. This is the ECS (Entity-Component-System) pattern, adapted for a scene graph.

Design decision: Components use a kind discriminator tag ('camera', 'assetInstance', 'text', etc.) rather than a class hierarchy. This makes them serializable as plain JSON and avoids inheritance complexity.

Components engine/components.ts

The NodeComponents interface is a discriminated union — a bag of optional component slots:

ComponentkindWhat it carries
camera'camera'Nothing. Its transform drives the viewport.
assetInstance'assetInstance'assetDefinitionId — references an asset definition
text'text'content, fontSize, alignment
bone'bone'length — for IK chains
mesh'mesh'Vertex data, triangles, UVs, bone weights
ghost'ghost'Invisible helper (IK target anchor)
table'table'Grid config: columns, rows, cell spans, column mapping
chart'chart'Chart type, data source, visual config, data keyframes

Why Frozen?

Components are Object.freeze()'d after creation (sceneNode.ts:443). To change a component, you must replace the entire object. This enforces immutable-update semantics — you can't accidentally mutate a component and break invariants elsewhere.

// WRONG — frozen, will throw in strict mode
node.components.text.content = 'new text'

// RIGHT — replace the whole component
node.components = {
  ...node.components,
  text: { kind: 'text', content: 'new text', fontSize: 24, alignment: 'left' }
}

Transforms

Local Transform engine/transform.ts

interface Transform {
  x: number        // horizontal offset from parent
  y: number        // vertical offset from parent
  rotation: number // radians, cumulative from parent
  scaleX: number   // multiplicative from parent
  scaleY: number   // multiplicative from parent
  localPivot?: { x: number, y: number }  // rotation/scale origin
}

The identity transform is { x: 0, y: 0, rotation: 0, scaleX: 1, scaleY: 1 }.

World Transform engine/worldTransform.ts

The world transform is computed by walking up the parent chain and composing each local transform:

world.x += rotateX(local.x * scaleX, local.y * scaleY, parentRotation) world.y += rotateY(local.x * scaleX, local.y * scaleY, parentRotation) world.rotation += local.rotation world.scaleX *= local.scaleX world.scaleY *= local.scaleY

Key function: composeChain(chain, localOf) — walks root-to-node, accumulating the world transform.

Dirty Flagging

Every node has _worldTransformDirty and _cachedWorldTransform. When a node's local transform changes, markDirty() cascades down to all descendants:

markDirty(): void {
  if (!this._worldTransformDirty) {
    this._worldTransformDirty = true
    this._cachedWorldTransform = null
    for (const child of this.children) {
      child.markDirty()  // cascade
    }
  }
}

The world transform is only recomputed when needed (lazy evaluation). This avoids recomputing the entire tree on every frame.

Inverse: relativeTransform()

Given a world transform and the parent's world transform, compute the local transform. Used when you know where a node should end up and need to figure out what local values produce that result.

Scene engine/scene.ts

A thin wrapper that owns the root node, camera node, and a flat Map<id, SceneNode> for O(1) lookup:

class Scene {
  id: string
  root: SceneNode      // the tree root
  camera: SceneNode    // exactly one per scene
  #nodes: Map<string, SceneNode>  // flat index

  getNode(id): SceneNode | undefined
  register(node): void    // adds to index
  unregister(nodeId): void // removes from index
}
Why a flat map? The tree is for hierarchy and transform composition. The map is for O(1) lookup by ID — critical when the animation evaluator or renderer needs to find a node quickly.

Traversal: walkPreOrder()

A generator that yields nodes in depth-first pre-order (parent before children):

function* walkPreOrder(root: SceneNode): IterableIterator<SceneNode> {
  const stack = [root]
  while (stack.length > 0) {
    const current = stack.pop()
    stack.push(...[...current.children].reverse())
    yield current
  }
}

Used everywhere: serialization, renderer rebuild, world transform computation, selection cycling.

Cycle Detection: wouldFormCycle()

Before reparenting, check if the new parent is a descendant of the node. If so, it would create a cycle:

function wouldFormCycle(node: SceneNode, newParent: SceneNode): boolean {
  for (let cursor = newParent; cursor !== null; cursor = cursor.parent) {
    if (cursor === node) return true
  }
  return false
}

This walks up from the proposed new parent. If it hits the node being moved, the reparent would create a cycle.

The Camera Node

Every scene has exactly one camera node. It is not special in the tree — it's just a SceneNode with a camera component. But its transform drives the viewport:

Camera PropertyViewport Effect
x, yPan (scroll the view)
scaleX, scaleYZoom (scale the view)
rotationLocked (not animatable)

The camera is animated in the timeline like any other node — it's not a special case in the engine, just a node the renderer knows to interpret as the viewport.

How the Renderer Uses the Scene Graph

The Pixi.js renderer (pixi/renderer/) maintains a Map<nodeId, PixiContainer> — one Pixi container per scene node. On engine events:

EventRenderer Action
SlideActivatedDestroy all containers, rebuild from walkPreOrder
NodeCreatedAdd one container
NodeRemovedDestroy container + descendants
TransformChangedRe-evaluate and apply one node
Time changeRe-evaluate ALL nodes at new time
The pattern: Engine fires events → Renderer subscribes → Renderer selectively updates Pixi containers. The engine never knows about Pixi. The renderer never mutates the engine. Clean separation via the event bus.

Recap

  • Tree: Nodes parent-child. Transform composition is automatic.
  • Components: Identity via frozen discriminated union slots, not class hierarchy.
  • Transforms: Local is relative to parent. World is composed up the chain. Dirty flagging avoids recomputation.
  • Camera: One per scene. Its transform = the viewport.
  • Scene: Thin wrapper with flat O(1) node lookup.
  • Renderer: Maps nodes → Pixi containers. Subscribes to engine events. Never mutates engine.
